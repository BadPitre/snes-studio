# SPEC_FORMATS — SNES Studio data formats

**Status:** v0 (Phase 1 — POC). This document is the living copy of sections 4-6
of `KIT_PHASE1_POC_MOTEUR.md`: THIS one is authoritative and follows the code.
Any divergence between the code and this spec is a bug in one or the other.

Every multi-byte value is **little-endian** (native 65816).

---

## 0. State of the format — v0.2 (Phase 2b, binary in ROM)

**Since Phase 2b, scenes and texts are byte-exact BINARY BLOBS**
(`engine/src/data/scenes.bin` / `texts.bin`), generated by `tools/datagen`
from the source project `demo/` (JSON + PNG — see `docs/TOOLS.md`) and
pinned into their banks by `engine/databanks.asm`. The Phase 1 divergences
(unpinned banks, symbolic Scene Table, C pointers instead of 24-bit far
pointers) are **resolved**: the engine reads the format of sections 1-2
below, as is, from ROM.

Remaining divergences and conventions, accepted in v0:

1. **Metatiles (Phase 5):** the tilemap's `t` value indexes the **metatile
   table** (4 BG u16 entries per tile: TL, TR, BL, BR), generated by datagen
   from a source tileset of 16x16 tiles (deduplicated 8x8 chars, max 512 —
   **char 0 is reserved transparent**). The source PNG is a grid of 16x16
   tiles (dimensions multiples of 16), indexed **row by row** (like the RPG
   Maker palette). Binary ids: `0..N-1` for the grid tiles, then the
   **autotile variants actually used** (Phase 5c, RM2003 format: 48x64 PNG,
   borders composed from 8x8 quarters, computed by datagen — the engine only
   ever sees ordinary metatiles), and last the transparent metatile (empty
   upper layer). 256 ids max in total (the tilemap indexes with a u8).
   Careful: do not name a symbol "metatiles" — it silently collides with an
   internal PVSnesLib symbol (maps.asm).
2. **Size constraint: minimum 20x15** (one screen, like RM2003), maximum 255
   (u8) per axis and **8192 tiles in total** (v0.7: the grids travel
   compressed and are decompressed into 8192-byte WRAM buffers — e.g. 90x90,
   64x128). Maps larger than the 32x32 VRAM window are streamed (see §4);
   smaller ones fit entirely inside the window (no streaming on that axis,
   the off-map area filled with char 0 — never visible, the camera is
   clamped).
3. **GFX compiled per scene (v0.4, Phase 5d)**: byte 1 of the Scene Header is
   the `gfx_set_id` — an index into the generated tables `gfx_chars[]` /
   `gfx_chars_sizes[]` / `gfx_metas[]` / `gfx_prios[]` / `gfx_pals[]`
   (`data_assets.c`). datagen compiles, for each scene, ONLY the tiles it
   uses (real VRAM budget: max 254 local ids, 512 chars, 8 palettes of 15
   colours per scene); scenes with identical content share the same set. The
   source PNGs may have up to 256 colours (RM2003 chipsets): the chars are
   spread over several palettes (bits 10-12 of the BG entries, agglomerative
   merging) and the full BG CGRAM (colours 0-127) is loaded per scene. The
   gfx assets stay generated C arrays — the spec does not (yet) define a
   binary format for them.
4. **Per-tile passability (Phase 5c, RM2003 model)**: the sidecar
   `assets/tilesets/<tileset>.json` declares `autotiles` (48x64 PNG), `solid` (X ids)
   and `above` (☆ ids, drawn above the hero, passable). The binary collision
   layer (§1.4) is **derived** by datagen: an upper tile present and not ☆ →
   its passability wins (bridges over water), otherwise the lower tile's.
   `tileset_prios[]` gives one byte per binary id (1 = ☆ → BG priority bit on
   the upper layer).
5. **A single scene bank** ($82): datagen refuses a blob larger than 32 KB;
   spilling into $83 (reserved, kit §3) will be implemented if needed.
6. **Order of 24-bit far pointers** inside structures: `[bank][addr lo]
   [addr hi]` — the same order as the Scene Table entries.

## 1. Binary scene format (v0)

### 1.1 Scene Table (v0.2)

At a fixed address known to the engine: **$82:8000** (start of bank $82).

```
Offset  Size    Field
0       2       scene_count (u16)
2       1       boot_scene_id (u8)   — scene loaded at start-up
3       1       reserved (u8)
4       4×N     entries: { bank (u8), addr (u16), reserved (u8) } per scene
```

*v0 → v0.2 evolution (Phase 2b): `boot_scene_id` added to the header — the
boot scene is data, not an engine constant.*

**M1 — multi-bank:** the table's format does not change (each entry's `bank`
field was always there), but scenes may now live OUTSIDE $82: datagen packs
them sequentially (sequential first-fit, a scene is atomic and must fit in a
32 KB bank) into $82 and then into extra banks allocated from $88 upwards.
Every far pointer in the Scene Header carries its own scene's bank; the
engine follows the pointers with no bank map.

### 1.2 Scene Header (CH2 — 33 bytes)

```
Offset  Size    Field
0       1       scene_type      (u8)  — 0x01 = TOP_DOWN. The only value in v0,
                                        BUT THE FIELD EXISTS ALREADY.
1       1       gfx_set_id      (u8)  — index into the generated gfx_* tables
                                        (v0.4; before: tileset_id/reserved)
2       1       map_width       (u8)  — in 16x16 tiles (max 255)
3       1       map_height      (u8)
4       3       ptr_tilemap     (far) — LOWER layer (1 u8/tile, ids §0.1)
7       3       ptr_collision   (far) — 1 byte per 16x16 tile (see §1.4)
10      3       ptr_actors      (far) — actor table
13      3       ptr_scripts     (far) — the scene's bytecode block
16      1       actor_count     (u8)
17      1       player_start_x  (u8)  — in tiles
18      1       player_start_y  (u8)
19      1       music_id        (u8)  — soundbank index, 0xFF = silence (Phase 4b)
20      3       ptr_warps       (far) — warp table (v0.2, Phase 4)
23      1       warp_count      (u8)
24      3       ptr_tilemap_upper (far) — UPPER layer (v0.3, Phase 5c;
                                        an empty cell = the transparent metatile id)
27      1       sprite_set_id   (u8)  — index into the generated sprite_*
                                        tables (v0.5; before: reserved)
28      5       slot_walk_anim  (u8 x5) — one byte per sprite SLOT (CH2):
                                        bits 0-6 = anim step length (display
                                        frames of hero movement / pixels
                                        walked for an NPC; 8 by default),
                                        bit 7 = stepping idle (the charset
                                        walks in place while standing)
```

*v0 → v0.2 evolution (Phase 4): the header grew from 20 to 24 bytes with the
warp table; byte 19 (reserved) became `music_id`. The snesmod soundbank (.it
modules converted by smconv) occupies bank $87 (kit §3); the music ids follow
the order of `project.musics`. A scene's music is (re)started at boot and at
every warp — the same id means no interruption.*

*Phase 5b evolution: byte 1 (reserved) became `tileset_id` — the tileset
(chars + metatiles + BG palette) is loaded per scene at boot and at every
warp, like the music.*

*v0.2 → v0.3 evolution (Phase 5c): the header grew from 24 to 28 bytes with
`ptr_tilemap_upper` — two scenery layers (RPG Maker 2003 model, see §0.4 and
§4). The scene blob gains a w×h grid (the upper layer).*

*v0.3 → v0.4 evolution (Phase 5d): byte 1 became `gfx_set_id` — the gfx
(chars, metatiles, priorities, palettes) are compiled PER SCENE (§0.3), and
the tilemap values are ids LOCAL to the scene's set.*

*v0.4 → v0.5 evolution (Phase 6): byte 27 became `sprite_set_id` — sprites
(OBJ chars + palettes) are compiled PER SCENE like the tilesets: only the
character blocks used by the scene (the player included, 5 max) are embedded,
and the actors' `sprite_id` is remapped to the local slot (§1.3, §5).*

*v0.5 → CH2 evolution: the header grew from 28 to 33 bytes with
`slot_walk_anim` — the per-charset walk parameters (`project.charset_anims`,
resolved per slot by datagen). The engine unpacks them at scene load
(`scn_aspd`/`scn_aidle`, scene.c) for the two walk steppers.*

### 1.3 Actor entry (v0.14 — 16 bytes per PAGE)

```
Offset  Size    Field
0       1       actor_type    (u8)  — 0x01 = static NPC (talks with A)
                                      0x02 = CONTACT trigger (v0.6):
                                      passable — the script runs when the
                                      hero steps on the tile
                                      0x03 = AUTO trigger (v0.6): the script
                                      runs when the scene is loaded (boot or
                                      warp)
1       1       x             (u8)  — in tiles
2       1       y             (u8)
3       1       sprite_id     (u8)  — character-block SLOT in the scene's
                                      sprite set (§5, v0.5 — datagen remaps
                                      the project block from the JSON to the
                                      local slot, player = 0)
                                      0xFF = INVISIBLE (v0.8): the actor uses
                                      no OAM slot at all.
                                      THE APPEARANCE IS INDEPENDENT OF THE
                                      TRIGGER (v0.8): a CONTACT or AUTO actor
                                      may carry a sprite (a chest, a sign, an
                                      NPC that walks up to the hero) and stays
                                      passable
4       2       script_offset (u16) — offset in the scripts block (0xFFFF = none)
6       1       direction     (u8)  — 0=down 1=up 2=left 3=right
7       1       flags         (u8)  — bit 7 = CONTINUATION (v0.10): this entry
                                      is an extra PAGE of the previous event;
                                      bits 0-2 = condition type: 0 none,
                                      1 switch ON, 2 switch OFF,
                                      3 variable >= value;
                                      bits 3-4 = MOVEMENT (v0.11):
                                      0 static, 1 random, 2 vertical,
                                      3 horizontal ("action key" NPCs only)
8       2       cond_idx      (u16) — switch (0-511) or variable (0-255)
10      2       cond_val      (u16) — compared value (type 3)
12      1       prio_speed    (u8)  — bits 0-1: priority (0 below the hero,
                                      1 same as the hero, 2 above);
                                      bits 4-7: speed 1-4 (0 = default 1)
13      1       reserved      (u8)
14      2       route_ofs     (u16) — custom route (movement type 4): offset
                                      of the [flags][freq][len][steps] blob
                                      in the scripts block, 0xFFFF = none
```

**v0.14**: the flags move the movement onto bits 3-5 (mask 0x38) — type 4 =
CUSTOM ROUTE, applied when the page becomes active (repeated or not depending
on the blob's flag). Priorities: *below the hero* = passable, interaction
while standing on it; *same as the hero* = blocks and is talked to face to
face; *above* = passable, OBJ priority 3 (in front of the upper layer). Only
the "same as the hero" ones block each other and block the hero.

**Pages (v0.10, RM2003 model)**: an event = 1..N consecutive entries (the
CONTINUATION flag on pages 2+). At any moment, the **last page whose
condition passes** is active — the others are inert (no sprite, no
interaction, no trigger). The engine re-evaluates the pages when a scene is
loaded and at the end of every script (`actors_resolve_pages`). This is the
mechanism behind an open/closed chest and a stateful NPC.

**Moving NPCs (v0.11)**: the ROM position is only the starting point — the
true position lives in WRAM (pixels). Movement: 1 px every other frame (half
the hero's speed); *random* = one step in a randomly drawn direction every
32-95 frames; *vertical*/*horizontal* = back and forth, turning around when
blocked. A step is refused onto: a solid tile, the hero's tile, the (runtime)
tile of another active actor, or off the map. Interaction and player
collision use the RUNTIME tile. The world is FROZEN during scripts and the
System menu (RM2003 model). Contact/auto triggers stay fixed.

### 1.4 Collision (v0.2)

One byte per 16x16 tile:

| Value | Meaning |
|---|---|
| 0x00 | passable |
| 0x01 | solid |
| 0x02 | warp trigger (passable — stepping on it triggers, §1.5) |

T1 (RM2003 directional passage): the byte carries the TYPE in the LOW nibble
(COL_TYPE, the values above — every engine test masks with & 0x0F) and the
CLOSED SIDES in the HIGH nibble (COL_SIDES): bit 4 + DIR_* (down 0, up 1,
left 2, right 3). A closed side is crossed NEITHER on the way out NOR on the
way in (the opposite of a direction is DIR ^ 1) — for the hero
(edge_blocked, tested on the CENTRE tile) and for moving events (mv_blocked).
Derived from the tileset sidecar (`dirs`, the same upper-not-☆ rule as
passability); never placed on a solid, and the warps' 0x02 overwrites the
whole byte.

Other extended types (water…) will come when needed.
Pipeline note (v0.3, Phase 5c): this layer is entirely DERIVED by datagen —
0/1 from the tileset's passability (sidecar, rule §0.4: an upper non-☆ tile
wins over the lower one), then 0x02 placed from the scene's warp table. There
is no longer an author-drawn collision layer (the `collision` field of old
scene JSON is ignored).

### 1.4 bis — Animated tiles (T1, data_tileanim.c)

Sequences from the sidecar (`anims`, GRID tiles only) resolved PER SCENE into
gfx-set chars: `ta_first[scene]` bounds the sequences, `ta_ffirst[seq]` the
frames, `ta_dest[seq*4]` = the 4 VRAM chars of the base tile, `ta_src[frame*4]`
= the 4 ROM chars of each frame (frame 0 = the base), `ta_mode` (0 = 1-2-3,
1 = 1-2-3-2), `ta_speed` (display frames per step). Engine tileanim.c: one
step = 4 DMAs of 32 bytes (one sequence per VBlank, normal path only — the
composed screen reuses the char region). The frames are FORCE-INCLUDED in the
scene's charset as soon as the base is placed there; datagen refuses a base
one of whose chars is shared (dedup) with a tile outside the sequence, and
requires the same palette bits between the base and the frames. Every
instance of the tile animates together (shared chars — the RM2003 water
model); 8 active sequences max per scene.

### 1.5 Warp entry (8 bytes per warp — v0.2, Phase 4)

```
Offset  Size    Field
0       1       x            (u8) — triggering tile (in 16x16 tiles)
1       1       y            (u8)
2       1       dest_scene   (u8) — index into the Scene Table
3       1       dest_x       (u8) — the player's arrival position (in tiles)
4       1       dest_y       (u8)
5       1       flags        (u8) — v0.16: bits 0-2 = the hero's arrival
                             direction (0 = keep, 1-4 = DIR_* + 1)
6       1       trans        (u8) — S18: screen transition — 0 fade
                             (default), 1 instant, 2 mosaic ($2106 BG1-3
                             coupled to the brightness)
7       1       reserved
```

Engine behaviour: when the player's centre tile ENTERS a tile with collision
0x02, the matching warp is looked up in the table; the transition is close →
load the target scene (VM vars reset, gvars kept) → open, according to the
trans field (S18): fade (the default, the historical setFadeEffect recipe),
instant (a hard cut), or mosaic — $2106 on BG1-3, the block size rising while
the brightness falls (16 steps, 1 frame each), and the reverse on arrival.
S18b — wipes (a black curtain, HDMA channel 2 on $2100, bands of scanlines):
3 = wipe_down (black descends from the top), 4 = wipe_up (black rises from
the bottom), 5 = wipe_center (two bands meet in the middle) — and the reverse
when opening. JSON: `"trans": "fade" | "none" | "mosaic" | "wipe_down" |
"wipe_up" | "wipe_center"` (absent = fade) on the warp entry, and the same
field on the warp / warp_var / screen / stage_open / stage_close event
commands. No re-triggering until the player has left and found a warp tile
again.
v0.16: on arrival, the hero's direction is the one in the flags — or KEPT
(RM2003's "Retain" model) if the flags are 0; scripted warps (WARP/WARPV)
always keep it. The arrival direction is CONSUMED by the warp that reads it:
a warp triggered with no prior request (closing a composed screen, loading a
save) cannot inherit one from a previous warp — and the engine static is
initialised explicitly (tcc-816 does not zero the BSS; a bare static keeps
the console's boot pattern, the source of the "black/invisible hero" bug when
returning from a composed screen).

### 1.6 Grid compression — RLE (v0.7)

A scene's three grids (`ptr_tilemap`, `ptr_tilemap_upper`, `ptr_collision`)
are stored as **RLE**: runs of `[count (u8, 1-255)][value (u8)]` pairs,
decoded when the scene is loaded into the engine's WRAM buffers (3 × 8192
bytes, screen off) up to exactly `w*h` bytes. datagen validates `w*h <= 8192`.
On RM2003-style maps the gain is massive (~85 % on the demo) — this is what
makes games the size of an RM2003 game possible inside 4 MB, together with
the multi-bank split to come.

## 2. VM v0 spec — the bytecode

### Philosophy

- The v0 VM does ONE thing: NPC interaction and dialogue. Nothing else.
- Every opcode: 1 opcode byte + fixed-size operands. Trivial decoding.
- Two categories: **immediate** opcodes (chained within the frame) and
  **blocking** opcodes (which hand control back to the main loop until an
  event — input, end of frame).
- Budget: never run more than ~32 immediate opcodes per frame.
  v0.15: budget exhausted = the VM **hands control back** and resumes on the
  next frame (the editor's LOOP loops with no blocking command are legal and
  run at 32 ops/frame, like RM2003 — no more debug halt here; an unknown
  opcode still halts).

### VM state (in WRAM)

```c
struct VmState {
  u8  active;          // 0 = inactive
  u8  bank;            // bank of the current bytecode
  u16 pc;              // program counter (offset within the bank)
  u8  wait_mode;       // 0=no, 1=waiting for A, 2=waiting for the textbox to close,
                       // 3=CHOICE in progress (cursor up/down, A confirms — v0.6)
  u8  vars[64];        // scene variables (reset when a scene is loaded)
  u8  gvars[64];       // global variables (persist across scenes)
  u8  choice_var;      // v0.6: destination variable of the running CHOICE
  u8  choice_count;    // v0.6: number of options (2-4)
  u8  choice_sel;      // v0.6: the option under the cursor
};
```

**C representation in v0 (`engine/src/vm.c`):** no `bank` field — the scene's
script block is already resolved into a far pointer (`scene_ctx.scripts`),
and `pc` is the offset inside that block (the same semantics as the binary
format: the offsets of jump opcodes and the actors' `script_offset` are
absolute within the scene's script block). Guard rail: 32 immediate opcodes
per frame at most, then the VM hands control back until the next frame
(v0.15); debug halt on an unknown opcode only.

### Opcode table — v0.6

**Variable byte (v0.6)**: bits 0-5 = the number (0-63), **bit 7 = GLOBAL
variable** (`gvars`, persists across scenes) — everywhere "var" appears
below. The assembler writes `v<n>` (scene) or `g<n>` (global). The RM2003
"give / own an item" pattern is a gvar: `SETVAR g<n> 1` to give, `JEQ g<n> 1
<label>` to test.

| Op | Name | Operands | Effect |
|----|-----|-----------|-------|
| 0x00 | END | — | Ends the script, the VM goes inactive, control returns to the player |
| 0x01 | MSG | text_id (u16) | **Blocking.** Opens the textbox, displays text `text_id`, waits for A to close |
| 0x02 | SETVAR | var (u8), val (u8) | var = val |
| 0x03 | ADDVAR | var (u8), val (u8) | var += val (8-bit wrap assumed) |
| 0x04 | JMP | offset (u16) | pc = offset (absolute within the scripts block) |
| 0x05 | JEQ | var (u8), val (u8), offset (u16) | if var == val → jump |
| 0x06 | JNE | var (u8), val (u8), offset (u16) | if var != val → jump |
| 0x07 | SETGVAR | var (u8), val (u8) | gvars[var] = val (historical alias of SETVAR g) |
| 0x08 | JGEQ | var (u8), val (u8), offset (u16) | if var >= val → jump (handy for counters) |
| 0x09 | CHOICE | var (u8), count (u8), count × text_id (u16) | **Blocking.** Shows 2-4 options (one per line, `>` cursor up/down), A confirms → var = the chosen index (0..count-1) |
| 0x0A | WARP | scene (u8), x (u8), y (u8), trans (u8) | Teleports the hero (a full reload) and **ends the script** — the scripts block changes with the scene. trans (S18): 0 fade, 1 instant, 2 mosaic |
| 0x0B | FACE | actor (u8), dir (u8) | Turns the actor (an index into the actor table) towards dir (0=down 1=up 2=left 3=right) |

*v0 → v0.6 evolution (an explicit request): CHOICE (RM2003's Show Choices),
WARP (scripted Teleport), FACE (event orientation), and the gvar bit on
variable operands — scripted step-by-step NPC movement arrives with the
"moving NPCs" work. In addition, outside the bytecode: `wait_mode` 3 =
VM_WAIT_CHOICE, and the NPC being talked to turns towards the hero (an RM2003
reflex, engine side).*

*The table above stops at v0.6; the opcodes added since (0x0C-0x4B) are
specified by their comments in `engine/src/formats.h`, which is the
authoritative list — extending this table has drifted for sixty opcodes
and pretending otherwise would be worse than saying so.*

**O-B — indirection.** Three additions for data-driven scripts (a party
loop reads "hero N's stats" without unrolling per hero):
- `VARSRC_VARVAR` (source type 8): `vars16[vars16[src]]`, accepted
  everywhere a value source is decoded (`varop_src`): VAROP, SETLOC,
  CALLF arguments, RETF, both sides of JCMP16.
- `VAROPI` (0x26, the number SYSMENU freed): VAROP with an indirect
  destination — `vars16[(u8)vars16[dstv]] = ... OP value(src)`. Same
  6-byte shape; a separate opcode keeps the common case's decoder
  untouched.
- `DBREAD`'s entry-source byte becomes a mode BITFIELD: bit 0 = entry is
  a variable index (the historic 0/1, value-compatible), bit 1 = the
  destination is indirect (`vars16[(u8)vars16[dst]]`).

**Texts (v0.7):** bank $86, at $86:8000, strings compressed with a
**bigram dictionary (DTE)**:

```
Offset      Size    Field
0           2       text_count (u16)
2           3×N     entries: { ofs (u16, relative to $8000), bank (u8) }
2+3N        256     pair table: 128 × 2 ASCII characters
(banks)     ...     encoded strings, terminated by 0x00
```

*M1 — multi-bank: the header (count + entries + pairs) lives in $86; each
string lives in the bank named by its entry — $86 first, then extra banks
allocated after the scene banks. (Before M1 the entries were 2 bytes and
everything fit in $86.)*

`text_id` indexes the entry table. Inside a string, a byte in 0x80-0xFF
denotes pair `(code & 0x7F)` in the table (2 RAW characters — the decoder is
not recursive); the textbox decodes into a WRAM buffer before rendering.
datagen picks the project's 128 most frequent bigrams (~40 % gain on French
text). v0 encoding: plain ASCII (32-126, accents in v1 with the final font).

**Phase 11 — windowskin (docs/SPEC_SYSTEME_UI.md §1):** when the project
declares a windowskin, its nine 2bpp tiles (a 9-slice: TL T TR / L C R /
BL B BR) follow the font in the BG3 chars (chars 97-105, same CGRAM palette
16-19). The textbox uses them to draw itself as a frame; the typewriter
(`text_speed` frames per character) reveals the text during the VM's TEXTBOX
wait — A completes it, then closes.

**v0.17 — displaying a variable (`\v[n]`, RM2003 model):** in the SOURCE
text, `\v[n]` (n = a 16-bit variable, 0-254) is encoded by datagen as
`[0x01][n+1]` (never a zero byte inside a string; bytes < 0x20 are opaque to
the DTE, no pair covers them). When decoding, the textbox inserts
`vars16[n]` in decimal (1 to 5 digits) into the buffer BEFORE the word wrap —
the layout follows the value. Works in messages AND in choices.

**T2 — special text codes (RM2003 model):** the same encoding rules as
`\v[n]` (control bytes < 0x20, opaque to the DTE, copied through by the
decoder) — they are interpreted by the typewriter, invisible to the word
wrap, and ignored by instant rendering (`text_speed` 0) and by choice option
lines, unless stated otherwise. An unknown code is a datagen ERROR.

| Source | Encoding | Effect |
|---|---|---|
| `\v[n]` | `[0x01][n+1]` | variable n (0-254) in decimal |
| `\s[n]` | `[0x02][n+1]` | speed: n frames per character (0-19, 0 = instant until the end) — resumes at the next character, forgotten at the next message |
| `\.` | `[0x03]` | short pause (15 frames) |
| `\|` | `[0x04]` | long pause (60 frames) |
| `\!` | `[0x05]` | suspends the reveal until A is pressed (the first A's "reveal everything" also stops here) |
| `\^` | `[0x06]` | the message closes WITHOUT a keypress once everything is revealed (also effective in instant rendering) |
| `\>` | `[0x07]` | start of an instant block |
| `\<` | `[0x08]` | end of an instant block |
| `\\` | `\` | a literal backslash |

Out of scope (no engine equivalent): `\N[n]` (no party system), `\$` (no
engine money — a variable plus `\v[n]` does the job), `\_` half-space (a
tiled font), `\C[n]` colour (the BG3 palettes beyond CGRAM 16-19 belong to
the tilesets — to revisit if a real need shows up).

**T2 — message by reference:** the `msg` command accepts `text_ref` (the name
of an entry in `texts.json`, the Tools > Textes catalogue) instead of `text`:
several commands then share the SAME entry in the text bank, editable from
the catalogue without touching the events. An unknown reference is a datagen
error.

**v0.9 (A2-P4) — 16-bit switches and variables, RM2003 style:**

| Opcode | Name | Operands | Effect |
|---|---|---|---|
| 0x0C | SW | idx u16, val u8 | switch idx (0-511) := val (0/1) |
| 0x0D | JSW | idx u16, expected u8, ofs u16 | pc = ofs if switch == expected |
| 0x0E | SET16 | var u8, val u16 | 16-bit variable var (0-255) := val |

**v0.16 (common events — global scripts, RM2003 model):**

| Opcode | Name | Operands | Effect |
|---|---|---|---|
| 0x21 | CALL | offset u16 | calls a sub-script (a common event body) — an 8-level return stack, debug halt when full (runaway recursion is a data bug) |
| 0x22 | RET | — | returns from a CALL; on an empty stack it acts as END |

The scripts block of EVERY scene now starts (offset 0) with the **table of
AUTO/PARALLEL common events**: `[n u8]` then n × `[type u8][switch u16][offset
u16]` (type 0 = Autorun, 1 = Parallel; datagen directive `CETAB`, an empty
table = a single 0x00 byte). Switch `0xFFFF` = no condition (the box
unchecked): the entry is ALWAYS active, as in RM2003 — an unconditional
Autorun runs forever (a title screen, a game over), an unconditional Parallel
is permanent.

- **Autorun** (type 0): when the VM is free, the engine starts the first one
  whose switch is ON — and RESTARTS it as long as the switch stays ON
  (RM2003 semantics: it is up to the script to turn its own switch off; the
  player is frozen meanwhile).
- **Parallel process** (type 1, v0.16): runs IN THE BACKGROUND every frame
  outside the System menu, without freezing the player — a second execution
  context (pc, waits, call stack) swapped with the main one around the
  interpreter (swap-in/swap-out); variables and switches are SHARED.
  Restarted from the beginning as long as its switch is ON. UI opcodes (MSG,
  CHOICE) are forbidden there — datagen refuses a parallel that contains one,
  transitively through CALLs.

The bodies of the common events referenced by a scene (calls — transitively —
and auto/parallel triggers) are emitted by datagen into the scene's scripts
block, terminated by RET; the 16-bit offsets stay local to the scene. A
common event can target "this event" (ROUTE/SETPOS/SWAPPOS 0xFF): resolved at
run time through `script_actor`, the actor that started the calling script
(0xFF in a parallel).

stated: `0x00-0x03` walk down/up/left/right, `0x04` at random, `0x05` towards
the hero, `0x06` away from the hero, `0x07` one step forward; `0x10-0x13`
turn, `0x14` 90° right, `0x15` 90° left, `0x16` about-turn, `0x17` 90° L/R at
random, `0x18` at random, `0x19` towards the hero, `0x1A` back to the hero;
`0x20/0x21` speed ±(1-4: 0.5/1/2/4 px/frame), `0x22/0x23` frequency ±(1-8: a

reflex are ignored), `0x2A/0x2B` phasing ON/OFF (only the map edge blocks);

charsets per scene). The ROUTE opcode carries [actor][flags][frequency
1-8][len bytes][steps…]; the route lives INLINE in the scripts block and
advances DURING scripts too (cutscenes), while wandering stays frozen. A
blocked walking step turns the NPC and is retried (or given up with "ignore
if blocked").

### 3.1 WRAM map — where the buffers live (v0.8, contractual)

| Area | Content | Constraint |
|---|---|---|
| `$7E:0000-1FFF` | PVSnesLib lowram (tcc registers, pads, VBlank) | untouchable |
| `$7E:2000-7FFF` | **tcc-816's `.bss`** (24 KB usable) | **hard ceiling `$8000`** |
| `$7E:8000-9AB4` | PVSnesLib variables, including **`oamMemory` (`$7E:9094`)** | untouchable |
| `$7F:8000-FFFF` | the engine's large buffers (`wram7f.asm`) | 32 KB |

**TOOLCHAIN TRAP (expensive, lived through):** tcc-816's `.bss` is allocated
in SLOT 2 (`$7E:2000-FFFF`) while PVSnesLib puts its own variables in SLOT 0
of the **same bank** (`$7E:8000+`). WLA allocates the two slots
**independently and does not detect the overlap**: a `.bss` that runs past
`$7E:8000` overwrites the OAM shadow **with not a single message from the
linker**. The symptoms do not look like memory corruption: the unused OAM
entries, zeroed out, become *visible* 16x16 sprites stacked at `(0,0)`, which
saturates the hardware limit of **32 sprites per line** on the first 16 lines
— the hero and the NPCs are then simply **deleted by the PPU**, as if the
engine were clipping them too early at the top of the screen.

Contractual consequences:
- The decompressed grids `scn_lower` / `scn_upper` / `scn_col` (3 × 8192
  bytes, §1.6) are declared in **assembly** in `engine/wram7f.asm`,
  RAMSECTION `BANK $7F ORGA $8000 FORCE`, and seen from C through `extern`
  (tcc-816 pointers are 24-bit far, so inter-bank access is transparent).
- `make` **fails** if a `.bss` symbol lands at `$7E:8000` or beyond (the
  Makefile's `checkwram` target) — the bound cannot be expressed in
  `hdr.asm`, since the PVSnesLib libraries are pre-compiled with this memory
  map.
- Any new buffer larger than ~1 KB goes into bank `$7F`.

**VBlank budget:** per frame: at most 1 streamed column + 1 streamed row of
metatiles (256 + 256 bytes, see streaming below) plus the OAM shadow (544
bytes, an automatic DMA from the PVSnesLib NMI) — within the DMA budget
(~4.5 KB). The full initial tilemap load (8 KB) happens with the screen off
(forced blank), outside the frame budget.

**Tilemap streaming (`engine/src/map.c`):** VRAM holds only a window of 32x32
metatiles (= the complete SC_64x64 tilemap, which is also the 512 px hardware
wrap area — so a VRAM char = the map coordinate mod 64, and the scroll
registers get the camera position as is). The window follows the camera 8
metatiles ahead of the visible edge; at each window step (max 1 per axis per
frame, guaranteed by the camera moving at 1 px/frame), the incoming
column/row is prepared in WRAM during the active frame then transferred at
VBlank through `dmaCopyVram7` (columns: VRAM increment +32 words, 2 segments
per char column; rows: +1 word, 2 segments per row).

## 4. Engine VRAM layout (v0)

The BG side below is an engine choice, not a data one — documented here
for reference. The OBJ side (vignette/battler chars, digit sheet,
weather blocks, their OAM entries and palettes) is GENERATED per
project since O-A: datagen computes `engine/src/data/vidmap.h` from
what the project's events actually use, and checks the scene sprite
sets and screen backdrops against it (PLANNING_VIDMAP.md). The numbers
quoted for those systems elsewhere in this document are the canonical
values the map emits when the system is in use.

| VRAM address (words) | Content |
|----------------------|---------|
| $0000 | BG1 tilemap, SC_64x64 — **upper layer** (8 KB). **Scenes with an EFFECT LAYER (S9)**: the region is REPURPOSED — the pattern's chars at $0000-$1000 (≤ 256, validated by datagen), a 32x32 map in the gap at $1C00; BG1 carries the pattern (scroll = drift, not the camera), and map.c no longer writes there. Register `data_effects.c` (always emitted): `eff_pic[]` (0xFF = none), `eff_blend[]`, `eff_par[]` (S11: scroll += camera >> n, 0 = fixed), `eff_dx[]`/`eff_dy[]` (an 8.8 step per frame). Entries carry the priority bit (the pattern in front of the sprites); blending: sub screen BG2+OBJ, tint/flash suspended. |

**S17 — PANORAMA (effect layer in "back" mode):** the same plan and the same
machinery as S9, but the pattern goes BEHIND the map instead of above it.
`eff_mode[]` (0 front, 1 back) and `eff_repeat[]` (1 repeated/scrolling, 0
fixed) are added to `data_effects.c`. In back mode: the pattern's map entries
do NOT carry the priority bit (BG1 low priority, BG1.0), there is no color
math (opaque), and `map.c` forces the priority bit on the WHOLE lower layer
(BG2.1) — the Mode 1 ordering then puts BG2.1 in front of BG1.0, so the
ground covers the panorama except on ERASED tiles (S10, transparent) which
let it show through. Sprites (OBJ prio 2) in front of everything. The
panorama lives on BG palette 7 (an image imported "with transparency", index
0 transparent). `repeat=0`: drift and parallax are forced to zero (a fixed
image). Constraint: as with S9, the scene loses its upper scenery layer (BG1
is the panorama).
| $1000 | BG3 2bpp characters (textbox font: char 0 transparent + 96 ASCII glyphs 32-127) |
| $1800 | BG3 tilemap, SC_32x32 (textbox) |
| $2000 | BG1+BG2 characters (shared 4bpp tileset) |
| $4000 | OBJ characters (4bpp sprites) |
| $6000 | BG2 tilemap, SC_64x64 — **lower layer** (8 KB) |

Video mode: Mode 1 with **BG3 at high priority** (bit 3 of $2105) — the
textbox goes above everything. **Two scenery layers (the RPG Maker 2003
model, Phase 5c)**: BG2 = the lower layer (the ground), BG1 = the upper
layer. Mode 1 ordering: BG1 prio 0 in front of BG2 but behind the prio 2
sprites (hero/NPCs); a ☆ tile gets the BG priority bit (0x2000) on the upper
layer and passes IN FRONT of the sprites. The two layers share the charset,
the palettes, the streaming window and the scroll (VBlank budget: 1 KB max
per frame, 2 layers).
**Multiple palettes (v0.4)**: the BG entries carry their palette bits (10-12),
baked by datagen; the full BG CGRAM (colours 0-127, 8 palettes of 16) is
loaded when the scene loads — then **colour 0 (the backdrop) is forced BLACK
(S10)**: BG tiles never draw index 0, and only an EMPTY cell of the lower
layer (the eraser, value -1) shows it. **CGRAM slots 16-19 are RESERVED for
the textbox font** (2bpp BG palette #4): datagen places no colour there
(palette 1 is avoided up to 7 clusters; at 8, the smallest cluster is housed
in palette 1 at indices 4-15, 12 colours max), and the engine reloads the
font's palette after every scene_load. The layout is declared in
`engine/src/vram.h`.

**Textbox (`engine/src/textbox.c`)**: rows 20-27 of the BG3 map (the bottom
of the screen, 64 px), text 28 columns × 6 lines max, word wrapping. Glyphs
have an opaque background (colour 1 of 2bpp BG palette #4, CGRAM 16-19); a
BG3 char = `1 + ascii - 32`. The font is extracted from pvsneslibfont
(PVSnesLib, MIT) into a C array (`data_font.c`).

## 4bis. SRAM saves (v2 — v0.9)

LoROM SRAM bank `$70`, **8 KB** (`SRAMSIZE $03`, a battery-backed cartridge).
**4 slots of 2048 bytes**:

| Offset | Size | Field |
|---|---|---|
| 0-1 | 2 | magic `"SG"` |
| 2 | 1 | version = **2** |
| 3-6 | 4 | scene, x, y, the hero's direction |
| 7 | 1 | reserved |
| 8-71 | 64 | gvars (8-bit global variables, a legacy) |
| 72-135 | 64 | switches (512 bits — v0.9) |
| 136-647 | 512 | 16-bit variables [256], little-endian (v0.9) |
| 648-649 | 2 | checksum: the 16-bit sum of bytes 0-647 (LE) |
| 650+ | — | reserved (outside the checksum) |

A slot is valid if the magic, the version AND the checksum all agree —
otherwise it is treated as empty. v1 saves (128-byte slots) are not migrated
(version ≠ 2 ⇒ empty).

## 5. "Game constants" audit — state at week 5

No game data is hard-coded in the engine: positions, maps, collision, actors,
scripts, texts and the boot scene all come from the data banks. What remains
in the engine code, accepted as **v0 engine constants** (they will become
generated parameters once the Rust tools exist):

- player speed of 1 px/frame and the pseudo-animation cadence (8 frames) —
  kit S2;
- the textbox geometry (rows 20-27, 28 columns);
- the System menu's vocabulary ("Sauvegarder", "Charger", "Slot n"…) — v0.7
  engine strings, like RM2003's built-in menu (configurable per project in
  v1+);
- the streaming window margin (8 metatiles);
- the VRAM layout (`vram.h`) and the hardware constants (a 256x224 screen,
  16 px tiles, a 64-char BG wrap).

**Sprites compiled per scene (v0.5, the RM2003 charset model)**: the
project's source sheet (`assets.sprites`) is a strip of **16x24 frames**,
organised into **character blocks of 12 frames**: 4 directions (0=down 1=up
2=left 3=right) × 3 steps (idle, step A, step B). The player is block 0. A
project may have many blocks — datagen compiles, for each scene, a **sprite
set** containing only the player block plus the blocks of its actors (**5
blocks max per scene**, otherwise an error), deduplicated across identical
scenes. Generated tables `sprite_chars[]` / `sprite_chars_sizes[]` /
`sprite_pals[]` (`data_assets.c`), indexed by `sprite_set_id` (header byte
27); loaded into VRAM/CGRAM at boot and at every warp, with the screen off.
Each set's data lives in its own generated file (`data_sprites{i}.c` /
`data_gfx{i}.c`): a ROM section cannot be split (32 KB), and splitting them
up lets wlalink spread the sets over the free banks — the project's asset
budget becomes the whole ROM instead of a single bank.

- **Metasprite**: a frame = 2 stacked 16x16 OBJs, anchored on the entity's
  tile with **8 px of overhang above** (the head overlaps the tile above, as
  in RM2003). A ☆ tile of the upper layer passes in front.
- **OBJ VRAM layout** (frames LOCAL to the set, 60 max): a group of 8 frames
  = 4 rows of 16 chars (rows 0-1: the 16x16 top halves, rows 2-3: the bottom
  halves — the frame's last 8 lines are empty). The frame f top OBJ: tile
  `((f&0xF8)<<3) | ((f&7)<<1)`; the bottom OBJ: `+32`.
- **OBJ palettes**: slot s of the set uses OBJ palette s — datagen re-indexes
  each block's colours (15 max plus transparent, merging the closest ones
  beyond that, with a warning) and emits the full OBJ CGRAM (colours 128-255)
  per set.
- **Walk cycle**: phase 0-3 → the step shown is idle, A, idle, B (advancing
  every 8 frames of movement).

**Metasprite convention (v0.5):** an actor's binary `sprite_id` is the
**local slot** of its block in the scene's sprite set (the source JSON
declares the project block; datagen remaps it); the idle frame displayed is
`sprite_id*12 + direction*3`, with OBJ palette `sprite_id`.

**Interaction (week 3)**: button A + an actor on the tile the player faces →
`actor_interact()`. The provisional milestone-S3 effect: switching colour 2
of the BG palette (grass) to a debug red, the CGRAM write deferred to VBlank.
Replaced by `vmStart(script_offset)` in week 4. Actors are solid (player
collision).
