# PHASE 1 KIT — Data-driven engine POC

> **Historical document.** This is the kit that opened the project: the
> plan for the proof of concept, written before any engine code existed.
> It is kept as a record of what was decided and why. It is NOT the
> current state — the VM described here has 8 opcodes, today's has around
> fifty, and the scene format has grown several fields since. The living
> truth is `SPEC_FORMATS.md`.

**Project:** SNES Studio (working name)
**Phase:** 1 — engine proof of concept
**Target duration:** 5 weeks (side project)
**Prerequisite:** Phase 0 validated (a working PVSnesLib toolchain, repo created)

---

## 1. Goal & kill switch

### Goal

Prove that the "fixed engine plus generated data" architecture works on
the SNES: a ROM whose behaviour (map, character, NPC, dialogue) is
entirely defined by **data** stored in ROM banks separate from the code.
Changing the data changes the game **without recompiling the engine**.

### Deliverables

1. A `.sfc` ROM: a scrolling map, a playable character, and 1 interactive
   NPC with dialogue.
2. The written format spec (this document, sections 4-6, kept up to date
   with reality).
3. The POC's data as commented C arrays (they will be generated by the
   Rust tools in Phase 2).

### Kill switch (end of week 5)

The POC passes if ALL of these are true:

- [ ] The ROM runs without a glitch in **bsnes accuracy mode** (not just
      Mesen2).
- [ ] Editing the data C arrays (map, NPC position, text) and rebuilding
      changes the game — with **zero changes to engine code**.
- [ ] Scrolling is smooth at 60 FPS (no tearing, no slowdown).
- [ ] The dialogue opens, closes, and the VM script runs correctly (test:
      an NPC that counts how many times it has been talked to, through a
      variable).
- [ ] You still want to carry on with the project.

If a technical criterion fails after reasonable effort → diagnose it
together before giving up. If criterion 5 fails → the project stops
cleanly, with real SNES knowledge earned.

## 2. Overall architecture

```
┌────────────────────────── ROM (.sfc) ──────────────────────────┐
│                                                                │
│  CODE (fixed, written once)           DATA (generated)         │
│  ┌──────────────────────────┐         ┌─────────────────────┐  │
│  │ Boot / init              │         │ Scene Table         │  │
│  │ Main loop                │  ──────▶│ Scene 0 (header +   │  │
│  │ Top-down module          │  reads  │   map + actors +    │  │
│  │ Dialogue engine          │         │   scripts)          │  │
│  │ Bytecode VM              │         │ Scene 1, 2, ...     │  │
│  │ Rendering (BG, sprites)  │         │ Assets (tiles, pal) │  │
│  └──────────────────────────┘         └─────────────────────┘  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

**The cardinal principle:** the code contains NO hard-coded game data. The
player's starting position, the map dimensions, the texts — all of it
comes from the data. That discipline is what makes the editor possible in
Phase 3.

### Main loop (pseudo-code)

```c
main:
  consoleInit()
  loadScene(0)                    // reads the Scene Table, initialises everything
  loop:
    readInputs()
    if (VM active)                // a script is running (a dialogue…)
      vmStep()                    // runs until a blocking opcode
    else
      updatePlayer()              // top-down module: movement + collision
      testInteractions()          // A facing an actor → start its script
    updateCamera()
    prepareOAM()                  // metasprites → OAM shadow
    WaitForVBlank()               // the DMA transfers go out here
```

## 3. ROM bank layout (LoROM)

Mode: **LoROM** (32 KB usable per bank, $8000-$FFFF). FastROM can be
turned on later without changing the organisation.

| Bank | Contents | Notes |
|------|----------|-------|
| $80 (0) | Engine code + vectors + ROM header | Handled by PVSnesLib (crt0, snes_rules) |
| $81 (1) | Engine code (continued) + lib | |
| $82 (2) | **SCENE TABLE + scene data** | The heart of the data-driven design |
| $83 (3) | Scene data (continued) | Room to grow |
| $84 (4) | Graphics assets: BG tiles + sprites | Loaded into VRAM by DMA |
| $85 (5) | Palettes + compiled tilemaps | |
| $86 (6) | Texts / dialogues | Kept separate to ease future localisation |
| $87 (7) | Soundbank (IT music) | smconv, pinned by the Makefile |
| $88+ (8-31) | **Multi-bank pool (M1)** | Scenes then texts overflow here; the rest serves the SUPERFREE sections (gfx). A 1 MB ROM (ROMBANKS 32). |

**In PVSnesLib practice:** the data goes into separate `.c` files with a
section directive to force the bank (see `snes_rules` and the examples
using `.section` / bank attributes). For the POC, one `data_scenes.c`, one
`data_assets.c`, one `data_texts.c` — each mapped to its bank in the
makefile.

**Access rule:** the code reads the data through far (24-bit) pointers.
PVSnesLib handles that, but keep in mind that a 16-bit pointer never
leaves its bank.

## 4. Scene binary format (v0)

Every multi-byte value is **little-endian** (native to the 65816).

### 4.1 Scene Table

At a fixed address the engine knows (the start of bank $82):

```
Offset  Size    Field
0       2       scene_count (u16)
2       4×N     entries: { bank (u8), addr (u16), reserved (u8) } per scene
```

### 4.2 Scene Header

```
Offset  Size    Field
0       1       scene_type      (u8)  — 0x01 = TOP_DOWN. The only value in v0,
                                        BUT THE FIELD EXISTS FROM THE START.
1       1       flags           (u8)  — reserved (0)
2       1       map_width       (u8)  — in 16x16 tiles (max 255)
3       1       map_height      (u8)
4       3       ptr_tilemap     (far) — bank + addr of the tile indices
7       3       ptr_collision   (far) — 1 byte per 16x16 tile (v0: 0=free, 1=solid)
10      3       ptr_actors      (far) — the actor table
13      3       ptr_scripts     (far) — the scene's bytecode block
16      1       actor_count     (u8)
17      1       player_start_x  (u8)  — in tiles
18      1       player_start_y  (u8)
19      1       reserved        (u8)
```

### 4.3 Actor entry (8 bytes per actor)

```
Offset  Size    Field
0       1       actor_type    (u8)  — 0x01 = static NPC (the only type in v0)
1       1       x             (u8)  — in tiles
2       1       y             (u8)
3       1       sprite_id     (u8)  — index in the metasprite table
4       2       script_offset (u16) — offset into the scripts block (0xFFFF = none)
6       1       direction     (u8)  — 0=down 1=up 2=left 3=right
7       1       reserved      (u8)
```

### 4.4 Collision (v0, deliberately simplistic)

1 byte per 16x16 tile: `0x00` = walkable, `0x01` = solid. The extended
types (water, one-way, warp triggers) come in v1 — do not over-design now.

## 5. VM v0 spec — the bytecode

### Philosophy

- VM v0 does ONE thing: NPC/dialogue interaction. Nothing else.
- Each opcode: 1 opcode byte plus fixed-size operands. Trivial decoding.
- Two categories: **immediate** opcodes (chained within the frame) and
  **blocking** opcodes (which hand control back to the main loop until an
  event — an input, the end of a frame).
- Budget: never run more than ~32 immediate opcodes per frame (the
  infinite-loop guard: a counter plus an emergency halt in debug).

### VM state (in WRAM)

```c
struct VmState {
  u8  active;          // 0 = inactive
  u8  bank;            // bank of the current bytecode
  u16 pc;              // program counter (offset within the bank)
  u8  wait_mode;       // 0=no, 1=waiting for A, 2=waiting for the textbox to close
  u8  vars[64];        // scene variables (cleared when a scene loads)
  u8  gvars[64];       // global variables (persist across scenes)
};
```

### Opcode table v0

| Op | Name | Operands | Effect |
|----|------|----------|--------|
| 0x00 | END | — | Ends the script, VM inactive, control back to the player |
| 0x01 | MSG | text_id (u16) | **Blocking.** Opens the textbox, shows `text_id`, waits for A to close |
| 0x02 | SETVAR | var (u8), val (u8) | vars[var] = val |
| 0x03 | ADDVAR | var (u8), val (u8) | vars[var] += val (8-bit wrap assumed) |
| 0x04 | JMP | offset (u16) | pc = offset (absolute within the scripts block) |
| 0x05 | JEQ | var (u8), val (u8), offset (u16) | if vars[var] == val → jump |
| 0x06 | JNE | var (u8), val (u8), offset (u16) | if vars[var] != val → jump |
| 0x07 | SETGVAR | var (u8), val (u8) | gvars[var] = val |
| 0x08 | JGEQ | var (u8), val (u8), offset (u16) | if vars[var] >= val → jump (useful for counters) |

Eight opcodes. That is all. The temptation to add more is the first trap
of the phase — every extra opcode waits until its need is proven.

**Texts:** an offset table in bank $86. `text_id` indexes the table; each
text is a `0x00`-terminated string. v0 encoding: plain ASCII (accents in
v1, with the final font).

### The canonical test script (the counting NPC)

The script that validates the whole chain — an NPC whose dialogue changes
with the number of interactions:

```
; var 0 = conversation counter
start:
  JGEQ 0, 2, seen_before   ; third time or more → a different text
  MSG  txt_hello           ; "Bonjour ! Je suis le premier PNJ de ce moteur."
  ADDVAR 0, 1
  END
seen_before:
  MSG  txt_again           ; "Encore toi ? On s'est déjà parlé plusieurs fois !"
  END
```

If that script works, the VM, the variables, the branches, the textbox and
the data pipeline are all validated at once.

## 6. Engine WRAM structures

```c
// Player
struct Player {
  u16 x, y;            // position in pixels (subpixels in v1 if needed)
  u8  dir;             // 0=down 1=up 2=left 3=right
  u8  moving;
  u8  anim_frame;
  u8  anim_timer;
};

// Camera
struct Camera {
  u16 x, y;            // top-left corner in pixels, clamped to the map edges
};

// Current scene (a WRAM copy of the header plus resolved pointers)
struct SceneCtx {
  u8  scene_type;
  u8  map_w, map_h;
  u8  actor_count;
  // resolved far pointers to tilemap, collision, actors, scripts
};
```

**VBlank budget (to respect from the POC on):** scrolling a map larger
than the screen means streaming the tile columns and rows that come into
view. Per frame: at most 1 column + 1 row of tilemap (~64 + 64 bytes) plus
the OAM shadow (544 bytes) — very comfortable within the DMA budget (~4.5
KB), but the habit of counting is acquired now.

## 7. Week by week plan

### Week 1 — Foundation & map display
- The `engine/` skeleton in the repo: a PVSnesLib makefile, `main.c`,
  console init.
- The `docs/SPEC_FORMATS.md` file: a copy of sections 4-6 of this kit (the
  spec lives in the repo and evolves with reality).
- Test data: a 32x32 tile map as a C array (a simple 8-16 tile tileset:
  grass, wall, path), banks $82/$84/$85.
- The engine reads the Scene Table, loads the tileset and palette into
  VRAM, shows the map (BG1, mode 1).
- **Milestone: the map is displayed from the data. Changing a tile in the
  C array changes it on screen after a rebuild.**

### Week 2 — Player & scrolling
- A 16x16 player metasprite (the Phase 0 character will do), read from the
  data (sprite_id, the header's starting position).
- Four-direction movement on the pad, constant speed (1 px/frame to start).
- The camera centred on the player, clamped to the map edges.
- Tilemap streaming during the scroll (THE technical piece of the phase —
  plan to spend time on it, lean on the "Map and Object Engines" wiki
  page).
- **Milestone: the character walks a 512x512 px map, smooth scrolling,
  validated on bsnes accuracy.**

### Week 3 — Collision & actors
- AABB collision against the collision layer (16x16). The character slides
  along walls (no corner sticking).
- Loading the actor table: the NPC appears at its position, facing its
  direction.
- Interaction detection: A + the player adjacent to the NPC + facing it.
- **Milestone: walls are solid, and pressing A facing the NPC triggers
  (for now) a simple background colour change — the hook is proven.**

### Week 4 — Textbox & VM
- Textbox: a window at the bottom of the screen (BG3 in mode 1, text on a
  dark background), an 8x8 font in the assets, appearing and disappearing.
- VM: the decode loop, the 8 opcodes, the VmState, the blocking mechanism
  (MSG hands back, the main loop routes inputs to the textbox).
- Wiring: NPC interaction → vmStart(script_offset).
- **Milestone: the canonical counting-NPC script works end to end.**

### Week 5 — Consolidation & verdict
- A full bsnes accuracy validation pass (plus Mesen2 in "accurate" mode
  too).
- Cleanup: the engine code no longer holds a single game constant (a quick
  audit: look for magic numbers).
- A second scene added to the Scene Table (same engine, another map,
  another NPC) to prove multi-scene support — even without being able to
  travel between them in game yet (warps come in Phase 4; changing
  scene_id at boot is enough).
- The spec updated with everything that changed along the way.
- A demo GIF plus a first public post (SNESdev forum / homebrew Discord).
- **Milestone: the kill switch is evaluated, GO/NO-GO decided for Phase
  2.**

## 8. Known traps & countermeasures

| Trap | Countermeasure |
|------|----------------|
| A VRAM write outside VBlank (works in a lax Mesen2, breaks on hardware) | EVERY transfer through the PVSnesLib DMA functions after WaitForVBlank; validate each step in bsnes accuracy, not only at the end |
| A 16-bit pointer running off its bank | Bulk data aligned per bank; far access for data, systematically |
| An infinite loop in the VM | An opcode counter per frame plus a debug halt |
| Scrolling that glitches at the map edges | Clamp the camera BEFORE computing the columns to stream; test all four edges systematically |
| Make not reconverting changed assets | `make clean` when in doubt; in Phase 2 the Rust tools will handle dependencies properly |
| Over-designing the formats ("what if one day we want…") | Each format's v0 covers the POC and nothing more. The scene_type field is the ONLY concession to the future |
